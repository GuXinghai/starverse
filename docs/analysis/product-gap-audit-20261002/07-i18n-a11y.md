## Findings

### I18N-01 — HIGH / I18N_A11Y: Enter on picker action buttons can select a model instead

- **Risk tier:** P1 product correctness.
- **Scenario:** Open the model picker, leave a selectable model active, focus Close, a favorite button, or a detail/filter action, then press Enter.
- **Incomplete loop:** Keyboard activation bubbles to `onDialogKeydown`; every non-input target enters the model-selection branch. The handler prevents the native button activation and calls `onSelectItem(active)` instead of the focused action. This can unexpectedly change the conversation route/model and close the dialog.
- **Evidence:** `src/ui-app/components/ChatAppComposer.vue:1493` opens the picker. `src/ui-app/components/ModelPickerDialog.vue:2360` installs the ancestor listener; `:2127` only excludes inputs/textareas/selects/contenteditable; `:2138` handles Enter, `:2148` prevents default, `:2149` selects. The Close button is at `:2365`–`:2370`, favorite action at `:2944`–`:2957`. `:2053`–`:2057` calls `commitSelection`; `:2043` awaits the selection command and `:2044`–`:2045` emits select/close. The production command is registered in `src/ui-app/app/appChatApp.logic.ts:315` and calls `onUpdateRouteSelection`; `:5985` persists the provider/model route for the active conversation.
- **Minimal repair:** Restrict model keyboard navigation/selection to the model list or an explicit listbox/combobox owner; let native action buttons activate themselves. Do not globally capture Enter for all non-input controls.
- **Layer:** UI only. Existing backend command behavior is usable; the wrong UI event invokes it.
- **Existing tests catch it:** No identified test covers Enter on an action button. Picker tests exercise pointer clicks, drag/drop, and one explicit Enter on the dialog root; that root test does not cover this scenario. Add keyboard activation assertions for Close, Favorite, detail tabs, and the selected model row.
- **Evidence strength:** Static, high confidence. No live keyboard execution or model/state mutation performed.

### I18N-02 — MEDIUM / I18N_A11Y: Core dialogs omit modal semantics and focus containment

- **Risk tier:** P2 product quality.
- **Scenario:** Open history Search or an attachment's Details using the keyboard; alternatively tab through the model picker to its last control.
- **Incomplete loop:** Search and attachment Details do not move focus into the newly opened dialog or restore the opener. Search has no Escape-close handler. Search, Details, and the picker lack a dialog role/name, `aria-modal`, background inertness, and Tab containment. Keyboard focus can remain behind the visual overlay or leave it; a screen reader receives no modal-dialog boundary. The picker does already focus its search input and restore its opener, so those parts are implemented.
- **Evidence:** `src/ui-app/components/SearchModal.vue:38` resets search state on open but has no focus management; its overlay/content is plain `div` at `:170`–`:171`, and the only key handler is the query's Enter at `:192`. `src/ui-app/app/appChatApp.logic.ts:2711`–`:2716` only toggles the open flag. `src/ui-app/components/DraftAttachmentDetailsDialog.vue:323`–`:330` has a plain overlay/content and only a bubbling Escape handler; its script has no focus management. `src/ui-app/AppChatApp.vue:1088` renders it directly. `src/ui-app/components/ModelPickerDialog.vue:2355`–`:2362` has plain overlay/content, while `:2119`–`:2151` handles Escape/arrows/Enter but not Tab. Positive comparison: `src/ui-app/components/SettingsModal.vue:24`–`:59` implements focus placement, Tab wrapping, and opener restoration, and `:93`–`:97` supplies modal semantics/name.
- **Minimal repair:** Apply a consistent dialog focus/semantics contract to these three reachable surfaces, including open/close, Tab/Shift+Tab, Escape where applicable, and background exclusion. Preserve the picker's existing model navigation and attachment conversion controls.
- **Layer:** UI only.
- **Existing tests catch it:** The focused `SettingsModal.test.ts:45`–`:62` covers its own trap/restore behavior, not these dialogs. No dedicated Search/Details component test was identified. The Electron DFC smoke at `scripts/smoke/electron-shell-smoke.mjs:510`–`:529` clicks open/close and inspects visibility/text, without keyboard or dialog-role checks. Picker tests do not assert Tab containment or dialog semantics.
- **Evidence strength:** Static, high confidence for missing contract; actual Tab traversal and assistive-technology output were not executed.

### I18N-03 — MEDIUM / I18N_A11Y: Search and manual-provider configuration bypass the selected language

- **Risk tier:** P2 product quality.
- **Scenario:** Use the default Chinese locale, open the translated sidebar Search action, then search/filter/rebuild the index; or configure a compatible provider and add a manual model.
- **Incomplete loop:** The entry points are translated, but Search's entire form/results/empty/loading surface is hardcoded English. Compatible-provider manual model inputs, capability choices, and request/reasoning profile controls mix translated actions with English labels/placeholders and internal values. These strings never flow through `t`/`tf`; switching language cannot update them. Several manual-model inputs have placeholders without persistent associated labels, which also leaves their purpose unclear after entry.
- **Evidence:** Default language is `zh-CN` in `src/shared/i18n/localeRegistry.ts:16`. Sidebar action uses `t('common.search')` at `src/ui-app/components/ConversationList.vue:254`, opening the real Search component through `src/ui-app/AppChatApp.vue:414`–`:422`. `src/ui-app/components/SearchModal.vue:173`–`:234` hardcodes title, Close, query, scopes and fuzzy/exact mode; `:241`–`:298` hardcodes filters, Rebuild index, loading and empty state; `:108`–`:122` hardcodes result labels. There is no i18n import. Reachable provider settings embed `CompatibleProviderSettingsPanel` at `src/ui-app/components/SettingsPanel.vue:2194`; the panel's `:740`–`:818` has bare manual inputs and English capability choices, and `:869`–`:924` hardcodes request/reasoning profile labels/preset explanations.
- **Minimal repair:** Translate the complete Search workflow and compatible manual-model/profile labels and display choices in both supported locales; keep wire identifiers unchanged. Add associated visible labels to manual inputs. Include localized loading/empty/rebuild/result text, rather than repairing isolated strings.
- **Layer:** UI and shared locale dictionaries only; backend behavior is already called by these controls.
- **Existing tests catch it:** No. `CompatibleProviderSettingsPanel.test.ts:159`–`:162` explicitly finds English placeholders and the literal `text` label, so it accepts this state. `scripts/i18n/hardcoded-allowlist.txt:32` excludes the whole Search component. The scanner only fails above 50 candidates (`scripts/i18n/check-hardcoded-ui-text.mjs:372`); its current 46 candidates pass. Locale parity checks do not assert that reachable components use translations. Add representative assertions under both locales, and replace blanket component suppression with narrow legitimate exceptions for repaired surfaces.
- **Evidence strength:** Static workflow evidence plus executed read-only i18n gates. Runtime language switching was not exercised.
- **Dedupe note:** Provider model/fact precedence, User Rules semantics, and raw ProviderFailure diagnostic presentation are outside this finding.

### I18N-04 — MEDIUM / I18N_A11Y: Favorite-model ordering has no keyboard alternative

- **Risk tier:** P2 product quality.
- **Scenario:** A keyboard-only user opens the model picker's favorite order editor and tries to move a model before another.
- **Incomplete loop:** Edit and Done are reachable buttons, but order changes only through HTML drag/drop. The draggable cards have no keyboard move action; the only card action is remove. Arrow keys are owned by the dialog's active-model navigation and do not reorder favorites. The reorder persistence path exists but cannot be reached through an order-changing keyboard action.
- **Evidence:** `src/ui-app/components/ModelPickerDialog.vue:2871`–`:2899` supplies `draggable`, drag/drop handlers and remove only. `:1115`–`:1125` performs the move exclusively in `onFavoriteDrop`; `:1088`–`:1095` emits an order only when dirty. `:2132`–`:2134` sends arrow keys to `onMoveActive`. Existing closure: `src/ui-app/components/ChatAppComposer.vue:1040`–`:1056` calls `ModelPrefsService.reorderFavorites` and refreshes the shortcuts; `src/next/modelPrefs/modelPrefsService.ts:463` calls the bridge's reorder method.
- **Minimal repair:** Add labeled Move up/Move down actions with boundary states and focus retained on the moved item; reuse the current ordering/save/persistence path.
- **Layer:** UI only.
- **Existing tests catch it:** No. `ModelPickerDialog.test.ts:636`–`:717` verifies synthetic dragStart/dragOver/drop/dragEnd plus a click on Done; it neither asserts nor requires keyboard reordering. Add a keyboard-only edit/move/save assertion with final order and focus.
- **Evidence strength:** Static, high confidence. The persistence path was traced but not executed or mutated.

## Recommended bounded repairs

1. Fix I18N-01 first: keyboard Enter must execute the focused control's action. Verify that Close/Favorite/detail/filter actions never invoke the selection command.
2. One subsequent UX/accessibility batch can standardize the three dialogs, localize Search/manual-provider forms, and add a non-drag favorite-order path. Acceptance should explicitly cover both locales and keyboard open/interact/close/restore, rather than treating existing i18n or Electron pointer-smoke PASS as sufficient.
